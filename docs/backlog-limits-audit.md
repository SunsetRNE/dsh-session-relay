# 待收/等待上限审计（2026-11-06）

起因：有会话的待收队列堆到 5–7 条，说明它已经落后很久；但插件只在 `peer_send` 回执里报「队列 N 条」，没有上限、没有落后判定，也没有在侧栏/看板露出。

## 已有限制（审计时）

| 入口 | 现状 | 结论 |
|---|---|---|
| 会话待收队列（`peer_send` / `/relay` / 汇报投递） | **无上限、无落后判定**，只报总条数和最早一条排队时长 | 本次补 |
| 发送限流 `RelayGuard` | 普通 8 次/10 分钟；主会话 3 倍；树内 40 次/10 分钟 | 够用，保留 |
| 新建会话 | 3 个/30 分钟 | 够用 |
| 汇报唤醒 | 12 次/10 分钟 | 够用 |
| 无人值守唤醒 | 16 次/小时/工作区，超了暂停 | 够用 |
| `peer_ask_user` | 每工作区最多 20 个 pending | 够用；问人不自动催 |
| `peer_mail` | 最多 500 条、30 天；未读默认 5 分钟提醒、最多 5 次 | 够用 |
| `peer_watch` | 进行中最多 50、存储 200、deadline 最长 7 天 | 够用 |
| issue 同步队列 | 最多 200 条、每次刷 20 条、退避最长 1 小时 | 够用 |
| 通知回执时限 | 默认 3 分钟、可自定义 10 秒–24 小时；最多 2000 条、保留 24 小时 | 够用 |
| 任务库 | 活动任务 500，超了归档 | 够用 |

## 本次补的判定与上限

- **硬上限**：目标待收队列 ≥ 8 条时，普通 `followup` / `queue` 发送直接拒绝，错误里给出条数、最早排队时长和改用 `mode=steer` 的建议；`steer` / `interrupt` 仍可插队。
- **落后**：待收 ≥ 4 条，或最早一条排队 ≥ 5 分钟 → `lagging`。`queue` 模式在落后时也拒绝（它不会叫醒对方）。
- **卡住**：最早一条 ≥ 30 分钟，或当前轮已跑 ≥ 30 分钟且待收不为空，或到硬上限 → `stuck`。
- **可见性**：`peer_list` 每行追加「待收 N（最早 X 前）⚠落后/⚠卡住」；看板快照给活跃会话带 `pending {count, oldestMs, runningMs, level, why}`；侧栏会话卡片显示「待收 N」胶囊（落后用警示色）。
- **回执**：`peer_send` 成功回显里如果目标已落后，会提示建议改用 steer 或等它处理。
- 判定只用可观测值（条数、最久排队、当前轮时长），不猜对方在做什么，也不替对方清队列。

## 强制插队（2026-11-06 补）

- `peer_send priority:"urgent"` / `/relay --urgent`：目标运行中直接 steer，不排本轮之后。
- 普通 followup 排队超过 60 秒仍未取走、目标仍在运行：自动从队列移出并 steer，给发送方回执；避免目标按旧目标继续白干。
- 只处理显式通知（kind=send），queue/urgent/待命消息不自动升级。

## 还没做（后续）

1. `/relay all` 群发目前逐个目标走同一套 `send` 检查；一个目标落后会失败，但不会先汇总/跳过。可加「跳过落后目标并汇总」。
2. `peer_mail force` 和汇报批 `ReportBatcher` 仍是独立投递路径，不经过待收上限；它们批次少，但可补每目标上限。
3. `peer_ask_user` 没有自动催办；用户离开时是否催属于产品决策。
4. 待收队列本身不能由插件删除（DSH 只允许按 id 撤回已排队消息）；硬上限是背压，不是清空。
